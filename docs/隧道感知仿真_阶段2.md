# 阶段 2：分类原因与只读净空诊断仿真

## 当前边界

这是实际 Gazebo Classic 射线雷达 → ROGMap → RViz/诊断的独立实验，不是人工拼出的 PointCloud2，也不是完整自动穿洞导航。

- **识别与车体尺寸分开**：ROGMap 分类不依赖 `.45 × .45 × .70 m`；这三个数只供另一个可选诊断器检查空间。
- 没有修改实车标定、串口、底盘、SLAM 输入或实车 TF 配置。
- `clearance.enabled` 默认 false；只在本实验配置中启用。它不发布通行许可、清障证据或速度。
- 本场景使用 Gazebo 真值雷达位姿，不运行 Point-LIO/FAST-LIO。目的是先排除里程计漂移，观察感知算法本身。
- 本实验没有底盘驱动插件，也没有 `cmd_vel` 话题。雷达架静止在世界原点，雷达高度 0.55 m。
- 全局记忆、入口门控、SLAM 回环关联及自动穿越**尚未接入本实验**。此前隔离 Nav2 开洞测试仍是另一个包。

## 一键运行

在本工程根目录执行；路径随当前用户自动确定，不写死 `/home/zst` 或 `/home/doublegun`：

```bash
bash run_passage_lab.sh
```

第一次会编译 `rog_map`、`sentry_terrain_bridge`、`sentry_passage_sim`、`rm_navigation` 并运行单元测试，之后是增量编译。所有产物在工程的 `.passage_lab/`，**不使用原有 `build/`、`install/`**。

无桌面时：

```bash
bash run_passage_lab.sh gui:=false rviz:=false
```

只构建检查：

```bash
bash run_passage_lab.sh --build-only
```

环境需有 ROS2 Humble、Gazebo Classic、`gazebo_ros`、`gazebo_plugins`、RViz 以及原 ROGMap 编译依赖。脚本不自动安装系统软件。

实验固定使用 **ROS_DOMAIN_ID=219、ROS_LOCALHOST_ONLY=1、Gazebo 11349 端口**。重复启动会因端口占用而拒绝；先在原启动终端 Ctrl+C，不能同时启动两份实验。

启动还会自动运行数据就绪检查。看到 `LAB READY` 才表示雷达、真值位姿、占据、分类和栅格均已收到。30 秒内缺少数据会打印 `missing`、`last_status` 并停止本次实验，不再让空白 RViz 一直挂着。一次就绪不代表后续永远正常，实时诊断仍会报告数据过期。

## 场景与图上内容

四个结构沿 y 方向排布，中心 x=2.6 m：

| y | 结构 | 场景真实尺寸 |
|---|---|---|
| 0 | 正常洞口 | 净宽 1.20 m、净高 0.95 m |
| 2 | 窄洞 | 净宽 0.30 m、净高 0.95 m |
| -2 | 低横梁 | 净宽 1.20 m、净高 0.50 m |
| 4 | 实心墙 | 没有通道 |

白色文字是**已知的场景标签，不是算法识别结果**。

RViz 中：

- 橙色立方体 `/rog_map/raw_occupied`：被观测到的三维占据体素。
- `/rog_map/classification_reasons`：二维柱的原始分类原因；绿色薄表面、红色实心墙、黄色疑似中空、紫色模糊障碍；蓝色空柱和灰色未知默认隐藏，可在 Namespaces 勾选。
- 黄色仅代表旧分类启发式的 `HOLLOW_TUNNEL`，不是已经通过整车净空验证。绿色薄表面也不保证最终代价为自由。
- `/terrain/grid` 默认关闭，打开 `Terrain grid` 可以看送往 Nav2 的标准二维栅格。最好单独观察，避免多个投影层互相覆盖。
- 本实验初始视角是倾斜三维视角。可先关闭 `Classification reasons`，观察屋顶与立柱之间的真实空隙，再打开原因层比较。

模拟场景的分类参数独立位于 `sentry_passage_sim/config/rog_map_lab.yaml`，不是实车推荐参数。特别是高度跨度不等于真实净高，不能照搬到实车。

## 点击检查一个直线区域

选择 RViz 工具 **Publish Point**，在地面/投影图上点击洞口附近。

诊断器在点击位置检查一段沿世界 x 轴、中心行程 0.8 m 的矩形扫掠空间。检查还包含车体长度，因此图上框长 1.25 m、宽 0.45 m、高 0.70 m。零额外人为尺寸余量；栅格体素边界仍保守取整。

这不是自动选洞口或自动估地面。探针固定使用本合成平地的高度；不适用于坡道、斜洞和复杂支撑面。不要拿这个探针直接控制实车。

另开终端，在工程根目录看诊断：

```bash
source /opt/ros/humble/setup.bash
source .passage_lab/install/setup.bash
export ROS_DOMAIN_ID=219 ROS_LOCALHOST_ONLY=1
ros2 topic echo /terrain/clearance/status
```

| 原因 | 含义 |
|---|---|
| `NO_PROBE` | 尚未指定检查区域 |
| `BODY_VOLUME_OCCUPIED` | 车体扫掠范围内查到占据体素 |
| `UNKNOWN_VOLUME_OR_SUPPORT` | 内部空间或地面支撑尚未完整观测 |
| `NO_GROUND_SUPPORT` | 预期支撑位置被观测为空闲，不能视作地面 |
| `STALE_OR_UNMEASURED` | 体素证据过期、无直接射线证据或时间无效 |
| `STALE_INPUT` | 整体点云输入停止或过期 |
| `OUTSIDE_ROLLING_MAP` | 检查区域超出当前局部窗口 |
| `GEOMETRY_PASS_OBSERVATION_ONLY` | 此次几何检查通过，仍不是进入许可 |

多帧确认要求**所查全部体素的最老直接观测时间前进**；反复读取同一快照不能加分。衰减得到的自由空间不算直接观测。虚拟地板也不算地面支撑。

**正常洞口在单一视角下仍可能是 UNKNOWN，不能为了让演示变绿就把未知当作自由。** 下一步应改善多视角覆盖与观测证据表达，而不是把尺寸门限调小。

## 自动检查

保持仿真运行，另一个已 source `.passage_lab/install/setup.bash` 的终端执行：

```bash
export ROS_DOMAIN_ID=219 ROS_LOCALHOST_ONLY=1
ros2 run sentry_passage_sim check_lab.py
```

该检查先最多等待 30 秒收齐数据，再对每个探针最多等待 15 秒。必须收到**对应探针坐标、输入年龄不超过 0.5 秒、检查体素数大于零**的结果。窄洞、低横梁和实心墙必须明确报告 `BODY_VOLUME_OCCUPIED` 且命中数大于零；`STALE_INPUT`、仅仅“没通过”均不能算验收成功。不发布运动命令，也不要求正常洞口在观测不足时强行通过。

首次本机 Gazebo 实测：收到 17114 个有限雷达返回、5730 个占据体素、241×241 地形栅格；123 格原始分类为疑似中空。正常洞口检查有 2866 个未知体素，未确认；窄洞、低横梁、墙分别查到 72、18、30 个车体范围内占据体素。具体数字随启动时刻和视角变化，不是固定验收阈值。

2026-10-14 最终复核：从 `.passage_lab` 一键编译启动，自检约 8 秒完成；严格四区域验收全部通过，输入年龄约 0.194～0.196 秒。21 项 C++ 单元检查和 3 项场景生成检查通过。早期检查脚本只要求“不通过”，会把输入过期误当成反例成功；现已修正为上述新鲜观测和真实占据命中的要求。

## 你这一部分需要检验什么

1. Gazebo 四种结构是否能看到，RViz 橙色占据体素是否与它们对应。
2. 只开三维占据显示，是否能从斜侧面看到正常洞口的屋顶和侧壁。
3. 打开原因层，区分黄色“疑似中空”与最终二维障碍，不把二者混为一谈。
4. 点击窄洞、低横梁，确认诊断报告障碍，而不是因为存在空点就放行。
