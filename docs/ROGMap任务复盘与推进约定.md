# ROGMap 任务复盘与推进约定

记录：2026-10-18。依据用户反馈与开发过程整理，约束后续工作，不是已完成实车验收的声明。

## 交付目标

在 doublegun 的 NUC 上，用真实雷达数据产生 ROGMap 通道证据，使 Nav2 最终全局 Costmap 对静态假墙形成可解释、可撤销的修正，规划能够利用缺口；之后验证入口许可和实际执行。

用户当前优先需要“在实车上运行看效果”。本地负责必要修改和基本核对，NUC 负责真实感知与融合验收。不是在本机完成部署，也不是不断完善合成演示。

## 问题与优化

| 问题 | 改进 |
| --- | --- |
| 最短真实链路未验证，就扩展太多记忆、门控、部署和测试内容 | 先拿到同一洞口的真实证据、最终地图与路径，再按实际阻塞点推进 |
| 合成消息和测试通过成了主要进度，却不能证明真实雷达产生证据 | 区分代码完成、本地检查、真实数据运行、实车效果；不可互相替代 |
| 仿真覆盖要求与现实遮挡条件脱节 | 短段逐步验证，不要求入洞前扫描完整条隧道，也不凭空把未观测区域视为安全 |
| 提到了北理/HERO，却未持续用相关源码解决具体瓶颈 | 对投影、自由空间、规划查询等问题，先核对相关开源版本和本地差异，再决定改动；引用项目不等于验证方案 |
| 用户要求 NUC 实测后仍不断增加本地检查项 | 完成必要构建与受影响回归后交付，不为增加测试覆盖率无限延迟运行 |
| 后置 TerrainLayer 可能重新封住修正区域，发现过晚 | 检查最终地图，区分结构投影冲突与真实新障碍，保留实时障碍否决 |
| 尺寸、许可和串口讨论挤占只读感知验证 | 分开“不驱动车的显示验证”与“允许穿越”；不用虚假尺寸伪造实车成功 |
| 本机绝对路径、重复命令、缺少文字增加了 NUC 操作负担 | 主指南先讲操作目的、界面观察与成功标准，完整命令放技术参考 |
| 将未开洞解释成安全拒绝后缺少推进 | 如实标记效果未通过，找最早失败环节，明确下一次修改要改变什么 |

## 后续工作规则

1. 下一轮真实反馈前，不扩展无关功能，不反复调整已确定的总体架构。
2. 用同一轮数据沿“扫描/TF → 三维证据 → 记忆/修正掩码 → 最终 Costmap → 路径”定位最早失败的一环，不一次修改多个无关参数。
3. 算法问题先对照相关开源实现及适用版本，不盲抄未经验证的行为，也不为绕过问题另起系统。
4. 只做与改动风险相称的构建和回归。测试用于防止回退，不替代真实验收。
5. 每次交付说明实际改变、已有证据、仍未证明的部分，以及 NUC 上最少需要的操作。
6. 分开显示原始地图、局部地形与最终 Costmap；半透明叠加和人工证据不是实测成果。
7. 真实数据看到开洞与新路径后，才能声明融合效果已验证；入口许可和实际穿越另行验收。
